# Codebase Documentation — AI Rabbit-Hole Explorer

**Status:** Living document. Reflects the codebase as of September 2026, **after** a
full build-and-run pass that took the project from "written but never executed" to
a working end-to-end system, verified by actually running it in Docker — not by
reading the source alone.

**Revision 2026-10-02:** goals re-prioritized by the project owner (§2: the primary
goal is learning a topic *without* falling into a rabbit hole; NLP research is
secondary). The tests, the ablation and the ambiguity eval were re-run against the
live system (§18, §19), and the gaps against the primary goal are recorded in §20.

**Revision 2026-10-03:** a real "association football" build was unusable for
learning: research-paper tangents, section headings as concepts, a near-random
learning path, and an unreadable canvas. Fixed across the pipeline: the Wikipedia
redirect bug (§11), source priority in the LLM context (§11 Aggregator), a
curriculum-style extraction prompt whose prerequisites become the edges (§12, one
LLM call per build instead of 2–4), orphan repair removed, off-topic and
connectivity filters, a root-anchored learning path (§12 Graph Builder), and a
canvas that reads as a route (§15). Validated with live builds on Groq for three
topics (§12). `backend/.env` now sets `LLM_PROVIDER_CHAIN=groq`: Gemini is excluded
to protect its daily quota.

**Generated by:** Systematic full-repository scan and analysis, followed by hands-on
execution, live debugging against real free-tier APIs, and a from-scratch rebuild
verification.

## 0. What Changed Since the Last Revision of This Document

The previous revision of this document described a "complete, working prototype"
based entirely on static code reading, and said so explicitly in its own §18: *"All
functionality claims in this document are derived from code inspection, NOT
validated execution."* That caveat turned out to matter more than it looked:

- **The backend could not import, at all.** `SourceDocument.metadata` collided with
  `Base.metadata` (a name reserved by SQLAlchemy's declarative base), so
  `import app.db.models` raised `InvalidRequestError` before a single line of
  application logic ever ran. Every entry point imports it. This was invisible to a
  static read because nothing about the code *looks* wrong — it only fails at
  class-definition time, under SQLAlchemy's own reserved-name check.
- **`requirements.txt` had never successfully `pip install`ed.** `fastapi==0.111.0`
  unconditionally requires `fastapi-cli>=0.0.2`, which requires `typer>=0.12.3`;
  `spacy==3.7.4` requires `typer<0.10.0`. No version of `typer` satisfies both — a
  hard, unconditional conflict, not a version drift issue.
- **The frontend had never once passed `tsc --noEmit`.** Six real TypeScript errors
  (unused vars/imports under `noUnusedLocals`/`noUnusedParameters`, a duplicate-key
  warning, and a missing `vite-env.d.ts` that broke every `import.meta.env` access)
  sat in files nobody had touched in months.
- **`GraphCanvas.tsx` called `cy.setStyle(...)`, which does not exist** on
  Cytoscape's `Core` type (the real method is `cy.style(...)`). This would have
  thrown on the very first node click in the browser, once the app could run far
  enough to get there.
- **The WebSocket real-time system was a guaranteed no-op**, not merely a scaling
  concern as previously written: `broadcast()` runs in the Celery worker process;
  the channel registry it wrote to lived only in the FastAPI process. In the
  project's own `docker-compose.yml` those are always separate containers, so
  *zero* pipeline-progress or node-expansion events were ever delivered to a
  browser, in any deployment this project has ever run.
- **The Celery `asyncio.run()`-per-task pattern crashed on the second task in any
  worker process** (including every `self.retry()`), not just under gevent/eventlet
  as the previous revision speculated — confirmed by triggering it live. The
  SQLAlchemy async engine's pooled connections bind to whichever event loop opened
  them; `asyncio.run()` opens a new one every call.
- **Both raw pgvector queries (`search.py`, `summarizer.py`) were silently broken
  and had never once executed successfully** — found only by clicking a node in an
  actual running browser session and reading the console. SQLAlchemy's `text()`
  bind-parameter parser mis-tokenizes `:vec::vector` (no space before Postgres's
  `::` cast operator): it reads the bind name as `ve`, not `vec` — confirmed via
  `text(sql)._bindparams.keys()`. This sent malformed SQL to asyncpg on every
  call, always raising `PostgresSyntaxError`. The previous revision's claim that
  these were "fixed: parameterized `:vec::vector` binding, no SQL injection" was
  true about injection safety but incomplete: the parameterized query never
  actually worked at all, in either endpoint, ever. Fixed with a one-character
  change (`:vec ::vector`, a space before the cast) in both files.
- Several external APIs had moved since this code was written: Wikipedia now
  rejects requests with no descriptive `User-Agent` (403), and its
  `page/mobile-sections` REST endpoint is fully decommissioned (also 403) — the
  latter was silently degrading every article to a one-paragraph summary. A latent
  `xml.etree.ElementTree` truthiness bug (`entry.find(...) or {}`) meant the arXiv
  fallback path — the thing that was supposed to catch Wikipedia failing — was
  *also* broken, on every entry, in a way that only manifests once you actually
  call it against live data.
- The user's own constraint (no paid APIs) forced a real architectural change: the
  O(n² − n) one-call-per-pair relation classifier is unworkable against free-tier
  rate limits (132 calls for a 12-node graph against, e.g., Gemini's 10 RPM would
  take ~13 minutes and exhaust a 250/day quota in two builds). This is now a
  single-call batched classifier by default, with the legacy pairwise mode kept
  only for the ablation study below.
- **Every configured LLM provider was silently dead**, confirmed live: Gemini's and
  Groq's hardcoded default model names had both been retired by their providers
  (404s), so every extraction/relation call fell through to `AllProvidersFailed` on
  every topic build, with the spaCy fallback masking it completely (graphs still
  "built", just with generic node text and, because the fallback path never
  produces edges, a completely disconnected graph that the frontend's fcose layout
  correctly rendered as a packed grid of overlapping labels — not a separate
  rendering bug). See §12 for the full root-cause chain, including a second
  Gemini-specific bug (default reasoning ate the whole `max_tokens` budget) and a
  Redis extraction-cache gotcha that means already-built topics won't self-heal.

All of the above are now fixed, and the fixes are exercised by an actual running
system, not asserted from reading. The sections below describe the system as it
exists now; where a specific defect from the previous revision was corrected, it's
called out inline rather than silently dropped, since seeing what was wrong and why
is part of orienting a new contributor to this codebase's actual risk areas.

## 1. Executive Summary

| Field | Value |
|-------|-------|
| **Project** | AI Rabbit-Hole Explorer |
| **Type** | Full-stack, NLP-powered, interactive knowledge graph web application |
| **Purpose** | **Primary:** let a learner learn a topic without getting lost in a rabbit hole of concepts, via a bounded knowledge graph, an ordered learning path, progress tracking and capped expansion. **Secondary:** an NLP research result (relation-classification ablation, §19). See §2. |
| **Architecture** | React SPA + FastAPI backend + Celery workers + PostgreSQL/pgvector + Redis |
| **Primary NLP pipeline** | Free-tier LLM chain (Gemini → Groq → Cerebras → Mistral → optional Anthropic) for concept extraction + batched relation classification, all-MiniLM-L6-v2 sentence embeddings, spaCy fallback (never fails, never costs) |
| **Current maturity** | **Runs end-to-end**, verified in Docker with zero API keys (worst case: Wikipedia + arXiv sources, spaCy extraction, no relation edges) and with the ablation-study harness producing real metrics |
| **Remaining known limitations** | No authentication (by design — see §10); a 150–300 pair hand-labeled ablation dataset is a human task the harness supports but doesn't fabricate (see §19) |

### What It Does
1. User types a topic on a landing page.
2. Backend spawns a Celery pipeline that fetches content from Wikipedia, YouTube,
   Reddit, Semantic Scholar/arXiv, and SerpAPI (web search) in parallel — the first
   two and last two need no API key to attempt (Wikipedia, arXiv), and connectors
   for the rest skip silently when unconfigured.
3. A free-tier LLM (or, absent any key, spaCy) designs a beginner curriculum: up
   to `initial_graph_node_cap` (12) concepts in learning order, each with its direct
   prerequisites, in **one** call. The prerequisites become the graph's
   `prerequisite_of` edges, with no separate relation-classification call by default
   (`relation_mode="curriculum"`). Off-topic outliers and nodes disconnected from the
   topic's root are dropped (see §12).
4. Concepts are deduplicated via cosine similarity, persisted as graph nodes with
   384-dimension sentence embeddings in PostgreSQL (pgvector extension).
5. A Cytoscape.js force-layout graph appears in the browser in real time via
   WebSocket, bridged across the FastAPI/Celery process boundary through Redis
   pub/sub (see §9).
6. Users can click any node to read AI-generated summaries at 3 depths, view
   original sources (including a YouTube notes/quiz generator, now wired into the
   UI — see §11), mark progress, or expand a node to drill deeper.

## 2. Project Identity and Goal

*(Re-prioritized 2026-10-02 by the project owner. The original design stated one
blended goal; there are now two, in a fixed order.)*

### Primary Goal: learn a topic without falling into a rabbit hole
Learning an unfamiliar topic from the open internet tends to sprawl: every concept
links to three more, and a learner ends up deep in a tangent with no sense of what
they were trying to learn or how far along they are. The app exists to **prevent**
that. Given one topic, it should give the learner:

- a **bounded** map of the topic (a capped number of concepts, not the whole web),
- an **ordered** route through it (the "Start Here" learning path, prerequisites first),
- a clear **"what next"** at every point (suggested next node, progress),
- **cheap orientation** before commitment (2-min summary before the 10-min/deep-dive),
- **controlled detours**: expanding a node is allowed, but it is capped, visibly
  subordinate to the main path, and easy to return from.

The product name describes the problem the app protects against, not a behaviour it
encourages. When a design choice trades exploration breadth against staying
focused, prefer staying focused.

### Secondary Goal: the NLP research result
The course deliverable is a measurable NLP result: how well cheap methods (keyword
co-occurrence, embedding similarity) type the relations between concepts compared
with an LLM, and whether a single batched LLM call loses accuracy against one call
per pair. That trade-off is real here because the free-tier-only constraint makes
O(n²) calls unworkable. This lives in `backend/eval/` (§19), together with a smaller
ambiguity-detection eval. The two goals are linked: `prerequisite_of` edges are what
order the learning path, so relation-typing quality directly limits how well the
primary goal can be met.

### Technical Goal
Given an arbitrary query string, automatically:
1. Retrieve multi-modal source documents (papers, videos, forums, encyclopedias).
2. Extract a bounded set of canonical concepts via LLM few-shot prompting.
3. Build a semantically deduplicated directed concept graph with labeled relation types.
4. Enable RAG-style summaries grounded in original source passages.
5. Surface emerging research trends via BERTopic clustering over publication abstracts.
6. Track a user's learning progress and suggest a topological traversal order.

### Intended Users
Students and self-learners who want to explore a new technical or scientific field.

### Core Domain Concepts

| Term | Definition |
|------|-----------|
| **Topic** | The user's free-text query. Owns the pipeline lifecycle: processing -> ready -> failed. |
| **Graph** | A versioned container of nodes and edges belonging to one Topic. |
| **Node** | A deduplicated concept extracted from source documents. Has label, category, description, 384-d embedding, importance score, and depth level. |
| **Edge** | A directed relation between two Nodes with a type and confidence score. Types: prerequisite_of, subtopic_of, enables, related_to, breaks. |
| **Summary** | A RAG-generated text for a Node at a chosen depth (2min / 10min / deepdive). Cached in both Redis and DB. |
| **Source Document** | Raw content fetched from an external connector (Wikipedia, YouTube, Reddit, paper, web). |
| **Source Chunk** | A word-window chunk of a Source Document with its own embedding, used as a RAG retrieval unit. |
| **Learning Path** | A topological ordering over prerequisite edges, with unconstrained nodes ordered by depth, distance from the root node, then importance. |
| **Expansion** | A user-triggered action that fires a Celery task to fetch new sources scoped to a specific node and merge new concepts. |
| **Trend Snapshot** | A BERTopic cluster over recent papers, with a 6-month growth-rate score. |
| **User Progress** | Per-node status record (not_started, in_progress, learned) tied to the anonymous user UUID. |

## 4. Architecture Overview

```text
Browser (React SPA)
    |
    |--- HTTP (Axios) ---------> FastAPI (port 8000)
    |                                  |
    |--- WebSocket ------------> ws.py channel manager <--- Redis pub/sub -----+
                                       |                                        |
                                   API Routers (v1/*)                          |
                                       |                                        |
                             +---------+-----------+                          |
                             |                     |                          |
                       PostgreSQL             Redis (DB 0)  <------------------+
                     (pgvector:pg16)          Cache + WS pub/sub bridge
                             |
                       Celery Worker
                     (Redis DB 1 broker,
                      Redis DB 2 backend)
                             |
                  +----------+----------+
                  |                     |
          Source Connectors         NLP Pipeline
          (Wikipedia, YouTube,      (Free-tier LLM chain,
           Reddit, Papers,          SentenceTransformer,
           SerpAPI)                 spaCy, BERTopic)
```

Communication patterns:
- **Sync (request/response):** Browser -> FastAPI REST endpoints. All endpoints are async.
- **Async pipeline kick-off:** FastAPI fires a Celery task with `.delay()` and returns HTTP 202 immediately.
- **Real-time push:** Celery worker calls `broadcast()`, which now **publishes to a Redis
  channel** rather than writing to an in-process dict — necessary because the worker
  and FastAPI are always separate processes. FastAPI's lifespan starts a background
  subscriber that relays each message to its own local WebSocket connections. See §9.
- **Polling fallback:** `GraphWorkspace.tsx` also polls `GET /topics/{id}` every 2.5
  seconds to catch the ready state, independent of whether WebSocket delivery
  succeeds.

## 5. Major Components

### 5.1 FastAPI Backend (backend/app/main.py)

What it does: Serves all HTTP and WebSocket requests. Handles startup (database
init, ANON_USER seeding, WebSocket pub/sub subscriber startup), CORS policy, and
application lifecycle.

Important details:
- Runs on python:3.11-slim via Uvicorn. `--reload` flag is used in Docker (dev mode only).
- CORS configured for http://localhost:3000 and http://127.0.0.1:3000 only. Any other origin is blocked.
- DB initialization happens via `init_db()` in the lifespan context, which also
  seeds the anonymous user (00000000-0000-0000-0000-000000000001), and the lifespan
  also starts `ws.run_subscriber()` as a background task (cancelled cleanly on
  shutdown).
- API is versioned under /api/v1. There is no /api/v2.
- `docker-compose.yml` now has real healthchecks (`pg_isready`, `redis-cli ping`, an
  HTTP check on `/health`) with `depends_on: condition: service_healthy`, so the
  backend can't start against a Postgres that isn't ready yet, and the worker can't
  start before `init_db()` has actually run.

### 5.2 Celery Worker (backend/app/worker.py, backend/app/tasks.py)

What it does: Runs long-running async NLP pipelines outside the HTTP request cycle.

| Task name | Trigger | Description |
|-----------|---------|-------------|
| tasks.build_topic_graph | POST /topics | Full pipeline: sources -> extraction -> graph build |
| tasks.expand_node | POST /nodes/{id}/expand | Fetches new sources for a node and merges new concepts, enforcing the expansion depth cap |
| tasks.detect_trends | After build_topic_graph completes | BERTopic clustering over linked papers |

**Corrected from the previous revision:** Celery's actual default execution pool is
**prefork** (separate OS processes — confirmed by worker log output showing
`ForkPoolWorker-N`), not threads as previously stated. This matters because of the
next point.

**Fixed critical bug:** All three tasks use `asyncio.run(coro)` to bridge sync
Celery context to async code. The SQLAlchemy async engine (`app/db/session.py`) is
a module-level singleton whose pooled asyncpg connections bind to whichever event
loop was running when they were opened — `asyncio.run()` opens a *new* loop every
call, so the second time a given forked worker process ran a task (including every
`self.retry()`, which lands back on the same process), it crashed outright with
`RuntimeError: ... attached to a different loop`, before the task's own logic ever
executed. This is not a gevent/eventlet-specific issue as the previous revision
speculated — it reproduced with Celery's actual default pool, live, in this
project's own container. Fixed by disposing the engine's connection pool *inside*
the same event loop, right before it closes (`tasks.py`'s `_run()`); disposing it
in a second, separate `asyncio.run()` call — the first fix attempted — doesn't
work, because by then the loop that owned those connections is already gone.

Retry policy: All tasks use max_retries=2 with countdown=10s. detect_trends uses max_retries=1, countdown=30s.

### 5.3 PostgreSQL Database (pgvector/pgvector:pg16)

Critical setup: The migrations/init.sql file runs ONCE on first container start to
enable the vector and uuid-ossp extensions. If this script does not run, all
embedding operations will fail.

Table creation: Done by SQLAlchemy's `Base.metadata.create_all()` at startup. There
are NO Alembic migration files (the `alembic` package is pinned but unused — see
§22). Schema changes require manual intervention or recreating the database.

**Fixed blocker:** `SourceDocument` declared a column literally named `metadata`.
`metadata` is reserved on any SQLAlchemy declarative base — `Base.metadata` *is*
the `MetaData` object every table's schema is registered against — so this raised
`InvalidRequestError` the moment `app.db.models` was imported, which is every
single entry point. The app could not start, at all, before this was fixed. It's
now `doc_metadata` in Python, mapped to the same `"metadata"` column name so no
migration was needed.

### 5.4 Redis

Three distinct logical databases:
- DB 0 (REDIS_URL): Application cache (source documents, LLM extractions,
  summaries) **and now the WebSocket pub/sub bridge channel** (`ws:broadcast`).
- DB 1 (CELERY_BROKER_URL): Celery task queue/broker.
- DB 2 (CELERY_RESULT_BACKEND): Celery task result storage.

**Fixed:** `graph_layout_key()` was defined in cache.py but never called anywhere —
removed as dead code.

### 5.5 Frontend SPA (frontend/src/)

Framework: React 18 with Vite (dev server). TypeScript throughout — and, as of this
revision, `tsc --noEmit` actually passes clean (it never had before; see §0 and
§18).

State: Zustand single global store (appStore.ts), **now persisted to
localStorage** (topicId, graphData, learningPath, pipelineStep, progress) via
Zustand's `persist` middleware, so a page refresh no longer throws the user back to
the landing page. No React Router — routing is still conditional on topicId.

Data fetching: React Query v3 for GET requests. Mutations via direct Axios calls.

Graph: Cytoscape.js with fcose (force-directed) layout algorithm.

Styling: Tailwind CSS + CSS custom properties for design tokens.

**Confirmed:** user_id is never set when a topic is created. All topics are effectively unowned (see §10 — this is a deliberate scope decision, not an oversight).

**New:** `status` and `clarification_options` are created via `Base.metadata.create_all`
(`db/session.py`), not an Alembic migration -- there is no migration tooling in this
repo (`migrations/init.sql` only enables the `vector`/`uuid-ossp` extensions). An
already-running dev Postgres volume will not pick up the new enum value or column on
its own; drop the volume (`docker compose down -v`) or manually `ALTER TYPE
topic_status ADD VALUE 'needs_clarification'` + `ALTER TABLE topics ADD COLUMN
clarification_options JSONB` before relying on this feature against an existing DB.

**Fixed:** `TopicCreate.prior_knowledge` is now actually threaded through to the
pipeline (`build_topic_graph.delay(topic_id, prior_knowledge)` -> `extract_concepts(..., prior_knowledge=...)`,
which appends an instruction to the extraction prompt). It is passed as a Celery

## 7. API Reference

**Base URL:** http://localhost:8000/api/v1
**WebSocket:** ws://localhost:8000/ws/channel/{channel_id}

**Authentication:** NONE. No token, session, or JWT validation on any endpoint.
`python-jose` and `passlib[bcrypt]` were in requirements.txt but were never used
anywhere — they've been removed (see §22) since keeping them implied an auth
system that doesn't exist. All endpoints are open. This is a deliberate scope
decision for a locally-run academic project, not a defect — see §10.

### Topics Group

**POST /api/v1/topics**
- Purpose: Create a new topic and start the processing pipeline.
- Request body: `{"raw_query": "string (2-500 chars)", "prior_knowledge": ["optional"]}`
- Response: 202 Accepted with TopicOut schema
- **Fixed:** `prior_knowledge` is now actually passed to the NLP pipeline (see §6, topics table).
- **New:** before creating the pipeline task, runs `nlp/intent.py::check_ambiguity()`
  -- a single synchronous LLM call (same free-tier chain as extraction) that checks
  whether `raw_query` has multiple distinct, unrelated common meanings (e.g.
  "Mercury" = planet vs. element vs. Roman god), as opposed to merely being broad
  within one domain (e.g. "Quantum Computing", which is never flagged). If
  ambiguous, the response has `status="needs_clarification"` and
  `clarification_options` populated, and `build_topic_graph` is **not** fired --
  the caller must resolve it via POST /topics/{id}/clarify first. If no LLM
  provider is configured or the call fails, this degrades to the old unambiguous
  behavior rather than blocking topic creation. See §11 (Aggregator) for the
  connector-selection skew this addresses (and the source-weighting skew it does
  not).

**POST /api/v1/topics/{topic_id}/clarify** -- new
- Purpose: Resolve a topic stuck in `needs_clarification` to one chosen sense, then
  start the pipeline exactly as POST /topics does for an unambiguous query.
- Request body: `{"chosen_query": "string (2-500 chars)", "prior_knowledge": ["optional"]}`
  (`prior_knowledge` is re-sent here rather than persisted on Topic, matching how
  POST /topics already handles it -- see §6.)
- Response: 202 Accepted with TopicOut schema (`raw_query`/`normalized_label`
  overwritten with `chosen_query`, `status="processing"`, `clarification_options`
  cleared).
- 404 if the topic doesn't exist; 409 if it isn't currently `needs_clarification`
  (guards against double-firing the pipeline on a retried/duplicate request).

**GET /api/v1/topics/{topic_id}**
- Purpose: Poll topic status during pipeline processing.
- Response: TopicOut or 404

**GET /api/v1/topics/{topic_id}/graph**
- Purpose: Fetch the full graph (nodes + edges + learning path) once ready.
- Response: GraphOut (graph_id, topic_id, version, nodes[], edges[], learning_path[])
- **Fixed:** `GraphOut.learning_path` is now typed `list[str]`, matching the actual
  values returned (it was declared `list[UUID]` while the code always sent
  strings — Pydantic silently coerced this, so it never caused a visible bug, but
  it was a real type/documentation mismatch).

### Nodes Group

**GET /api/v1/nodes/{node_id}/summary?depth=2min**
- Depth options: 2min (3 chunks, ~150 words), 10min (6 chunks, ~500 words), deepdive (12 chunks, ~1200 words)
- Caching: Checks Postgres, then Redis, then generates via the free-tier LLM chain (§12).
- Side effects: May call an external LLM API; writes to summaries table.

**POST /api/v1/nodes/{node_id}/expand**
- Response: 202 {"status": "queued", "node_id": ..., "graph_id": ...}
- Side effects: Fires `expand_node.delay(node_id, graph_id)` Celery task.

**GET /api/v1/nodes/{node_id}/sources**
- Response: Array of source document dicts ordered by relevance.

### Search

**GET /api/v1/graph/{graph_id}/search?q={query}&top_k=8**
- Purpose: Semantic search within a graph using pgvector cosine distance.
- Encodes query with SentenceTransformer; runs cosine distance against nodes table.
- Uses parameterized `:vec ::vector` binding — injection-safe, but **this endpoint
  never actually executed successfully before this pass**: the missing space
  before `::vector` made SQLAlchemy mis-parse the bind parameter name (see §0,
  §21.17), and every call raised a 500. Fixed and verified live: a real search
  query against a built graph now returns ranked results.

### Progress

**POST /api/v1/progress/{user_id}/{node_id}**
- Body: {"status": "not_started|in_progress|learned"}
- Note: Frontend hardcodes user_id = '00000000-0000-0000-0000-000000000001'.

**GET /api/v1/progress/{user_id}/graph/{graph_id}**
- Returns all progress records for a user on a graph.

### Trends

**GET /api/v1/trends/{topic_id}**
- Returns BERTopic trend snapshots ordered by growth rate descending.
- Returns empty array if detect_trends has not run or found insufficient papers.

### Videos

**POST /api/v1/videos/{source_document_id}/extract**
- Generates structured notes, key concepts, and quiz from a YouTube transcript via
  the free-tier LLM chain.
- **Fixed:** now called from the frontend (`NodeDetailDrawer.tsx`'s Sources tab, per
  YouTube source) — was previously a fully dead API path.

### Health

**GET /health**
- Returns {"status": "ok", "environment": "development"}

## 8. Major Workflows

### Workflow 1: Topic Creation and Graph Build

**Purpose:** User enters a topic -> backend builds a full knowledge graph -> frontend displays it

**Trigger:** User submits form on LandingPage.tsx -> POST /api/v1/topics

**Flow:**
1. [FastAPI] Runs `check_ambiguity(raw_query)` -- new. If the query has multiple
   distinct, unrelated common meanings, creates the Topic with
   status="needs_clarification" and returns the candidate senses instead of
   proceeding; [Frontend] LandingPage.tsx renders a picker in place of the search
   form, and calling POST /topics/{id}/clarify with the chosen sense re-enters this
   flow at step 2. Unambiguous/unavailable-LLM queries skip straight to step 2.
2. [FastAPI] Creates Topic record with status="processing"
3. [FastAPI] Fires `build_topic_graph.delay(topic_id, prior_knowledge)` -> returns HTTP 202
4. [Frontend] setTopic() stores topic_id (now persisted to localStorage); renders GraphWorkspace
5. [Frontend] useWebSocket() connects to ws://localhost:8000/ws/channel/{topic_id}
6. [Frontend] Polling loop starts (every 2500ms): GET /topics/{topic_id}

--- Celery Worker ---

7. Runs 5 connectors in parallel via asyncio.gather():
   - Wikipedia -> up to 5 articles (no key required; sends a descriptive
     User-Agent, which Wikimedia now requires -- see §11)
   - YouTube -> up to 5 videos (requires YOUTUBE_API_KEY; skipped if absent;
     transcript fetch now runs in a thread executor, not blocking the event loop)
   - Reddit -> up to 5 posts (requires REDDIT_CLIENT_ID; skipped if absent)
   - PapersConnector -> Semantic Scholar (fallback: arXiv -- its XML parsing bug is
     fixed, see §11)
   - WebConnector -> SerpAPI (requires SERPAPI_KEY; skipped if absent)
8. WebSocket broadcast: {event:"progress", step:1} -- via Redis pub/sub (§9)
9. Deduplicates source documents by URL; persists to source_documents table
10. WebSocket broadcast: {event:"progress", step:2}
11. Concatenates first 1000 chars of 8 source docs; calls `extract_concepts()`
    - Tries the free-tier LLM chain (Gemini -> Groq -> Cerebras -> Mistral ->
      optional Anthropic), each skipped if its key is unset
    - Fallback path: spaCy NER + noun chunks if every provider is unset or fails
12. WebSocket broadcast: {event:"progress", step:3}
13. Deduplicates concepts by cosine similarity (threshold 0.92); applies
    `initial_graph_node_cap` (now actually enforced -- previously defined but never
    applied)
14. Creates Graph and Node records
15. Classifies relations: **one batched LLM call** for the whole node set by
    default (previously one call per ordered pair -- O(n^2 - n), unworkable
    against free-tier rate limits; see §12). Edges below `relation_confidence_threshold`
    are discarded; if no LLM is available, this now correctly yields zero edges
    rather than a fully-connected hairball (see §6, edges table)
16. Computes degree centrality -> sets importance_score per node
17. Chunks + embeds source docs; creates NodeSource links by similarity
18. Computes topological sort -> learning path
19. Sets topic.status = "ready"; commits transaction
20. WebSocket broadcast: {event:"graph_ready", graph_id, learning_path}
21. Fires detect_trends.delay(topic_id) for async trend analysis

--- Frontend (on WebSocket "graph_ready", or the 2.5s poll -- whichever arrives first) ---

22. Calls GET /topics/{id}/graph -> receives GraphOut
23. Calls GET /progress/{user}/graph/{graph_id} -> loads saved progress
24. setGraphData() updates Zustand store -> triggers GraphCanvas re-render
25. GraphCanvas useEffect detects new nodes/edges; calls cy.add() incrementally
25. Runs fcose layout only on new elements; preserves existing node positions

**Decision points:**
- If no source docs fetched: build_graph raises ValueError -> task fails -> status="failed"
- If no LLM key is configured: spaCy fallback runs for extraction, and relation
  classification correctly produces zero edges rather than the previous unintended
  fully-connected fallback (see §6)

**Failure paths:**
- Pipeline exception -> status="failed" -> broadcast error -> Celery retries up to
  2x with 10s delay. **Fixed:** retries no longer crash the connection pool (see
  §5.2) -- confirmed by triggering a real retry and watching it succeed cleanly.
- All retries fail -> Topic permanently stuck in "failed" state (no UI for retry) --
  unchanged, a real gap.

**Verified live, with zero API keys configured** (the worst case): Wikipedia +
arXiv sources were fetched (no key needed for either), spaCy extracted 10 concepts,
relation classification correctly produced 0 edges (no LLM available), and the
graph reached `status: "ready"` end-to-end in under 30 seconds.

### Workflow 2: Node Expansion (Rabbit-Hole Drill-Down)

**Trigger:** User clicks "+ Expand" in NodeDetailDrawer -> POST /nodes/{id}/expand

**Flow:**
1. [FastAPI] Validates node exists; fires expand_node.delay(node_id, graph_id) -> 202
2. [Worker] Checks the expansion depth cap (`max_expansion_depth`, now actually
   enforced -- previously defined in config but never checked, so expansion could
   recurse indefinitely). If reached, broadcasts `expansion_complete` and stops.
3. [Worker] Broadcasts {event:"expanding", node_id, message} -- **now published to
   both the graph_id channel and the topic_id channel**, since the frontend only
   ever subscribes to topic_id (a channel mismatch that meant expansion events were
   silently dropped even after the WebSocket bridge itself was fixed)
4. [Worker] Fetches sources scoped to node.label (max 3 per connector)
5. [Worker] Extracts new concepts from combined text
6. [Worker] Filters out near-duplicates by **embedding cosine similarity** against
   every existing node (previously an exact lowercase label match, which let
   semantically identical concepts like "Neural Network" and "Neural Networks"
   both into the graph)
7. [Worker] Takes up to 6 new concepts; encodes embeddings
8. [Worker] Creates new Node records at depth = parent.depth_level + 1
9. [Worker] Creates Edge records (relation_type="subtopic_of", confidence=0.8)
10. [Worker] **Recomputes degree centrality over the whole graph** (existing +
    new nodes/edges), not just the new nodes -- previously every expanded node
    kept `importance_score`'s default of 1.0 forever, and the parent's score never
    reflected its new children
11. [Worker] Commits; broadcasts {event:"nodes_added", parent_node_id, new_nodes[], new_edges[]}
12. [Frontend] mergeNewNodes() deduplicates by id and adds to graphData
13. [GraphCanvas] cy.add() adds new elements; runs fcose layout (randomize:false)

**Fixed:**
- Depth cap now enforced (was: never checked).
- Dedup is now embedding-based (was: exact lowercase string match).
- Centrality is now recomputed for the whole graph after expansion (was: never
  recomputed post-initial-build).
- Dead import `from app.nlp.graph_builder import build_graph` removed (it was
  imported but never called in this path).
- Channel mismatch fixed: expansion events now reach the channel the frontend
  actually listens on.

### Workflow 3: Node Summary Generation

**Trigger:** User clicks a node -> selects Summary tab -> React Query fires GET /nodes/{id}/summary?depth=2min

**Flow:**
1. Check Postgres: SELECT summary WHERE node_id=? AND depth=?
2. If found: return cached summary
3. If not: check Redis key "llm:summary:{node_id}:{depth}"
4. If Redis hit: deserialize, create DB record, return
5. If miss: generate:
   a. Retrieve top-k source chunks by pgvector cosine similarity to node.embedding
   b. Format passages with citation indices [1], [2], ...
   c. If no passages: return node.description_short as fallback
   d. Call the free-tier LLM chain with SUMMARY_PROMPT (async now -- the previous
      sync Anthropic-only client blocked the event loop; see §11)
   e. Cache in Redis (30-day TTL); persist to summaries table
6. Return SummaryOut

**Failure paths:**
- If no LLM provider is available: returns first 3 passages concatenated (no synthesis)
- If no chunks found: returns node description or "No content available"

### Workflow 4: Trend Detection

**Trigger:** Automatically after build_topic_graph completes via detect_trends.delay(topic_id)

**Flow:**
1. Get latest graph for topic
2. Get all nodes in graph
3. Join NodeSource -> SourceDocument WHERE source_type='paper' AND published_at IS NOT NULL
4. Bail if < 10 papers found
5. Filter to last 24 months; bail if still < 10
6. Run BERTopic.fit_transform(abstracts)
7. Count papers per cluster in two windows (>6 months ago vs last 6 months)
8. Compute growth_rate = (recent - older) / older
9. Take top 5 TrendSnapshot records by growth_rate; **for each, embed its top-words
   label and link it to the nearest node by cosine similarity, setting
   `linked_node_id` and that node's `is_trending = true`** (previously both were
   always left at their defaults -- see §6, nodes and trend_snapshots tables)

**Key limitation:** Will silently skip for most topics (insufficient paper data; max 5 papers per source in initial fetch) -- unchanged.

## 9. WebSocket Real-Time System

**Location:** backend/app/api/ws.py

**Design (rewritten):** Real-time events are produced by Celery tasks, which run in
a separate container/process from FastAPI. The previous design had `broadcast()`
write directly to an in-memory `_channels: Dict[str, Set[WebSocket]]` registry --
but that registry only exists in whichever process imports the module, so a
broadcast from the worker wrote into a dict no browser-facing process ever read.
**Every WebSocket event this app ever produced was silently lost**, in every
deployment configuration this project has run in (the default `docker-compose.yml`
always separates `backend` and `celery_worker` into different containers).

The fix: `broadcast()` now `PUBLISH`es a JSON envelope (`{channel_id, payload}`) to
a single Redis pub/sub channel (`ws:broadcast`). FastAPI's `lifespan` starts a
background task (`run_subscriber()`) that `SUBSCRIBE`s to that channel and fans
each message out to *that process's* local `_channels` registry -- which is
exactly the mechanism the WebSocket endpoint itself reads from. This works for any
number of FastAPI/worker replicas, not just the current one-of-each setup, and it
required no new infrastructure (Redis was already a required dependency).

A second, independent bug meant this fix alone wasn't sufficient for node
expansion: `expand_node` published its events to the `graph_id` channel, but the
frontend (`GraphWorkspace.tsx`) only ever subscribes to the `topic_id` channel.
Expansion events are now published to both.

```python
_PUBSUB_CHANNEL = "ws:broadcast"
_channels: Dict[str, Set[WebSocket]] = defaultdict(set)  # local to this process
```

**Dead connection cleanup:** the local fan-out (`_deliver_locally()`) catches
exceptions per-connection, collects dead ones, and removes them from the set --
unchanged from before.

**Heartbeat:** Frontend sends "ping" every 25 seconds. Server responds "pong".

**Reconnection:** `useWebSocket.ts` now reconnects with exponential backoff (1s,
2s, 4s, ... capped at 15s) on an unexpected close. Previously there was none at
all -- one dropped connection meant the user missed every subsequent event until a
manual page reload.

**Verified live:** submitted a real topic through the running stack and watched the
pipeline-progress indicator advance through all four steps via the browser's
WebSocket connection, confirming the Redis bridge actually delivers cross-process.

Frontend hardcodes UUID '00000000-0000-0000-0000-000000000001' in client.ts. Backend seeds this user at startup. All progress data is shared globally across any client.

- Any user on the network can read any topic's graph, summaries, and progress.
- Any user can mark progress for any node belonging to any user.
- With zero auth, there is no meaningful data isolation.

## 11. Source Connectors (External Integrations)

All connectors implement: `async fetch(query, max_results) -> list[RawDocument]`

### Wikipedia (connectors/wikipedia.py)
- API: MediaWiki OpenSearch + REST summary + classic `action=query&prop=extracts` (see below)
- Auth: None required, but **a descriptive `User-Agent` header is now required** --
  Wikimedia rejects requests with no User-Agent, or a generic default like
  `python-httpx/x.y` (what httpx sends if you don't set one), with a 403. Every
  request this connector made was being blocked outright until this was fixed.
- **Fixed content-quality regression:** the REST `page/mobile-sections/{title}`
  endpoint this connector used to call for full article content has been fully
  decommissioned by Wikimedia (403 "Mobile Content Service is decommissioned").
  This was silently degrading every article down to its one-paragraph summary
  extract. Replaced with the classic `action=query&prop=extracts&explaintext=1`
  endpoint on the same host, which returns the full plain-text article. Verified
  live: the "Quantum computing" article's captured text went from ~800 characters
  to hitting the existing 8000-character cap.
- **Fixed 2026-10-03 (redirect titles fell back to one sentence):** OpenSearch
  often returns a *redirect* title (e.g. "Association football (soccer)"). The
  REST summary follows redirects on its own; `action=query` doesn't unless asked.
  The full-text request returned an empty extract, and the article silently
  degraded to its one-sentence summary: 181 characters for the football build,
  whose graph was then built almost entirely from arXiv abstracts. Now sends
  `redirects=1`. Verified live: the same query returns the full article (8000, the
  cap). Two stale layers were also fixed, since either would have hidden this. The
  Redis key is now `source:wikipedia:v2`, so old short extracts aren't served for
  the rest of their 7-day TTL. `aggregator.persist_documents()` now replaces a
  stored document's text when a fresh fetch of the same URL is longer; it used to
  reuse the old row forever, because URLs never change.
- Text cap: 8000 chars per document. Caching: 7-day Redis cache.
- **Status: CONFIRMED WORKING**, verified against live Wikipedia, not just read.

### YouTube (connectors/youtube.py)
- API: YouTube Data API v3 + youtube-transcript-api
- Auth: Requires YOUTUBE_API_KEY. Skips silently if absent.
- **Fixed:** `_get_transcript()` was a blocking/synchronous call inside an async
  method, called directly (no `run_in_executor`), which would stall the asyncio
  event loop for the duration of every transcript fetch. Now runs via
  `loop.run_in_executor()`.
- **Status: PARTIALLY CONFIRMED** (no key was available to test against live data
  end-to-end during this pass; the blocking-I/O fix and the frontend UI wiring for

### Reddit (connectors/reddit.py)
- Library: PRAW (synchronous)
- Auth: Requires REDDIT_CLIENT_ID + REDDIT_CLIENT_SECRET. Skips silently if absent.
- Wrapped in run_in_executor (correct, unchanged). **Fixed:** used the deprecated

### Papers (connectors/papers.py)
- Primary: Semantic Scholar Graph API; Fallback: arXiv Atom XML API
- Auth: Optional SEMANTIC_SCHOLAR_API_KEY
- **Fixed a real, previously-latent bug:** the arXiv XML parser used the pattern
  `(entry.find("atom:title", ns) or {}).text`, intending `or {}` as a safe fallback
  for a missing element. But `xml.etree.ElementTree.Element` defines `__len__`
  (its number of *child elements*) and no `__bool__`, so any leaf element with text
  but no child elements -- title, summary, published date, every author's name --
  is falsy even when `find()` successfully found it. `or {}` therefore always fired,
  and `{}.text` raised `AttributeError` on every single entry. This meant the arXiv
  fallback -- the thing meant to catch Semantic Scholar failing -- was itself
  completely broken, discovered only by actually calling it against live data
  (unauthenticated Semantic Scholar calls are rate-limited to 429 almost
  immediately, so the fallback path is exercised on nearly every real run). Fixed
  with an explicit `is not None` check (`_el_text()` helper) rather than a
  truthiness shortcut.
- **Status: CONFIRMED WORKING**, verified against live data for both APIs.

### Web (connectors/web.py)
- API: SerpAPI (/search). Requires SERPAPI_KEY. Skips silently if absent.
- Limitation: Only fetches title + one-line snippet. No full-page content retrieval.
- **Status: CONFIRMED WORKING when key provided** (per original documentation;
  not re-verified live in this pass since no SerpAPI key was available), low
  information density either way.

### Aggregator (connectors/aggregator.py)
- Runs all 5 connectors via asyncio.gather(*tasks, return_exceptions=True).
- Per-connector exceptions are caught and logged; aggregator continues.
- URL-based deduplication applied across all results.
- **Verified live:** with zero API keys, correctly aggregated 10 documents (5
  Wikipedia + 5 arXiv) for "quantum computing" while YouTube/Reddit/SerpAPI logged
  their "not configured -- skipping" warnings and Semantic Scholar's 429 fell
  through to the (now-fixed) arXiv path.
- **Known limitation, partially addressed:** the aggregator has no concept of query
  intent -- it fans out to whichever connectors are configured, and whichever
  documents survive each connector's `max_per_source` cap and the extraction
  prompt's 2000-char truncation window implicitly define "the topic". The
  quantum-computing example above is a real instance of this: a mainstream,
  broadly-known topic still ended up represented entirely by 5 Wikipedia + 5 arXiv
  documents, simply because those were the two connectors with no key requirement.
  `nlp/intent.py`'s ambiguity check (see §7, §8 Workflow 1) fixes the subset of this
  problem where the query itself has multiple distinct, unrelated senses (e.g.
  "Mercury") by asking the user to disambiguate before any connector runs. It does
  **not** fix source-weighting/truncation skew for a query that is unambiguous but
  niche or sparsely covered by the free connectors -- that remains open.
- **Partially addressed 2026-10-03 (LLM context sampling,
  `build_combined_context()`):** the equal round-robin across source types
  meant 5 arXiv abstracts got as much prompt space as the encyclopedia. With the
  Wikipedia redirect bug, they got ~70% of the football build's context. The
  "Mercury planet" build was likewise all microlensing research. The context now
  takes turns in `_SOURCE_PRIORITY` order (wikipedia → youtube → reddit → web →
  paper, so papers only fill what's left). A Wikipedia turn is 3× larger
  (`_SLICE_MULTIPLIER`), covering an article's lead and first sections. Docs under
  `MIN_CONTEXT_DOC_CHARS` (300, i.e. search-result snippets) are skipped whenever
  anything longer exists. Every source still gets a turn before any gets a second,
  which keeps the original fix against one source silently defining the topic.
  arXiv is still *fetched* for every topic: trend detection (BERTopic) needs papers,
  and classifying "research topic or not" would cost an LLM call. It's just
  de-prioritised for extraction.

## 12. NLP Pipeline

### LLM Provider Layer (nlp/llm.py) -- new

Concept extraction, relation classification, and summarization used to call the
Anthropic SDK directly and only. The user constraint driving this rebuild was no
paid API usage, and Anthropic has no free tier -- so this is now a
provider-agnostic client trying an ordered, configurable chain of **free-tier**
providers, each skipped if its API key is unset:

| Order | Provider | Model (default) | Why this slot |
|---|---|---|---|
| 1 | Gemini | gemini-flash-latest | 250K TPM, 1M context -- most headroom on the free tier |
| 2 | Groq | openai/gpt-oss-20b | 30 RPM, very low latency |
| 3 | Cerebras | gpt-oss-120b | No card needed; catalog is more volatile, kept third |
| 4 | Mistral | mistral-small-latest | ~50K TPM |
| 5 | Anthropic (optional) | claude-3-5-haiku | No free tier -- only used if a key is actually set |
| 6 | spaCy / passage concatenation | local | Already implemented; never fails, never costs |

Gemini, Groq, Cerebras, and Mistral all expose an OpenAI-compatible
`/chat/completions` endpoint, so one `httpx`-based client (`complete_text()` /
`complete_json()`) covers all four -- no per-provider SDK.

**Both hardcoded default models above were dead (confirmed live, not just read):**
`gemini-2.5-flash` 404s with *"no longer available to new users, use
models/gemini-flash-latest"* even though it still appears in `/models`, and
`llama-3.3-70b-versatile` 404s with `model_not_found` -- Groq's catalog rotated
away from Meta Llama chat models entirely (`GET /v1/models` shows only
`gpt-oss-*`, `qwen/qwen3.8-27b`, `allam-2-7b`, and non-chat audio/guard models
now). With every provider failing, every call fell through to `AllProvidersFailed`
and then to the spaCy fallback below, on every single topic build. That fallback
never fails, so nothing about the UI signals an error -- graphs still build, just
with generic node text (`"A key concept related to {topic}."`, `category: "Other"`)
and, critically, **zero edges** (`classify_relations_batched()` returns `[]` when
`AllProvidersFailed`, not a stub graph). An edgeless graph is what actually made the
frontend look broken: `GraphCanvas.tsx`'s fcose layout treats every disconnected
node as its own component and packs them into a tight grid with no visible
edges -- that grid-of-overlapping-labels look is fcose behaving correctly on a
genuinely edgeless graph, not a separate rendering bug. Fixed by pointing at
`gemini-flash-latest` and `openai/gpt-oss-20b` (verified live against both
accounts' actual `/models` listings).

That model fix alone wasn't sufficient for Gemini: `gemini-flash-latest` reasons
by default, and those (invisible, not returned in `message.content`) thinking
tokens count against `max_tokens`. At the extraction call's `max_tokens=1024`,
thinking alone could consume enough of the budget to leave as little as ~180
characters for the actual answer, truncating the JSON mid-string
(`json.loads` raising "Unterminated string ...") and *still* falling through to
the spaCy path even with a working model. Fixed by adding
`"reasoning_effort": "none"` to Gemini's request body (`_Provider.extra_body`,
merged into the JSON payload in `_post_chat_completion`) -- confirmed live this
drops `finish_reason` from `"length"` to `"stop"` with full, valid JSON every
time. Groq's `gpt-oss-20b` is also a reasoning model but didn't need this: it
comfortably fit real content in 1024 tokens in testing, and it rejects
`reasoning_effort: "none"` outright (`400`, must be `low`/`medium`/`high`), so
it's left alone rather than papering over a provider-specific quirk.

Cerebras' `gpt-oss-120b` returns `402 Payment Required` ("Payment required to
access this resource") on the configured account -- a billing/quota state on
that specific Cerebras account, not a code defect, and not fixed here. It's
harmless as long as Gemini or Groq succeeds first in the chain (both now do),
since a failed provider just falls through to the next one.

**The same truncation failure mode recurred on Groq, confirmed live on a second
topic ("Football") after the Gemini fix above was already deployed.** Gemini hit
`429 Too Many Requests` (free-tier RPM/RPD quota, expected under heavy testing)
and the chain correctly fell through to Groq -- but Groq's `gpt-oss-20b` is
*also* a reasoning model, and at `extract_concepts()`'s `max_tokens=1024` its
thinking tokens plus a full 6-10-concept JSON array occasionally overran the
budget too (`"Unterminated string starting at: line 39 ..."`), silently
degrading that build to the spaCy fallback despite a provider actually
responding. Fixed two ways: `extraction.py`'s extraction call now requests
`max_tokens=3072` (was 1024 -- generous headroom for reasoning overhead plus
verbose descriptions across up to 10 concepts), and Groq's `_Provider.extra_body`
now sends `{"reasoning_effort": "low"}` (Groq's API rejects `"none"` outright --
`400`, must be `low`/`medium`/`high` -- so `"low"` is the closest available
equivalent to Gemini's `"none"`). Re-verified live afterward: a fresh
football-related topic produced real descriptions/categories and 6 real edges
across 8 nodes on the first try.

One more gotcha this surfaces: `extract_concepts()` caches its result in Redis
keyed on `topic + prior_knowledge + supporting_text[:500]`
(`llm_extract_key`, `ttl_llm_cache`). A topic built while the models above were
dead has its bad (spaCy-fallback) extraction cached under that key, and — since
there is no "rebuild topic" endpoint, `POST /topics` always creates a new `Topic`
row rather than refreshing an existing one — re-querying the *exact same* topic
string will keep serving the cached bad result even after this fix, both from
that cache entry and from the old `Topic`/`Graph` rows already persisted for it.
Confirmed live: re-posting `"Agentic AI"` after the fix still returned the old
generic-description, zero-real-edges graph, while a never-before-seen query
(`"Agentic AI systems overview 2026"`) produced real LLM descriptions/categories
and 9 semantically real edges on the first try. A topic built before this fix has
to be recreated under new query text (or the Redis cache flushed) to see corrected
output -- it will not self-heal.

Each provider is
client-side rate-limited against its published free-tier RPM/TPM via a thread-safe
token bucket (Celery's prefork pool means multiple OS processes may call in, each
running its own event loop -- the bucket's state is guarded by a plain
`threading.Lock`, correct across both threads and processes-with-their-own-loops,
while callers wait for capacity with `asyncio.sleep` so they never block their own
event loop). `AllProvidersFailed` is raised only once every configured provider has
failed, so callers can fall back to their existing local path.

The Anthropic branch uses the native SDK, imported lazily inside the function that
needs it so a missing or outdated `anthropic` package can never block application
startup, and its synchronous client call is wrapped in `asyncio.to_thread()` so it
doesn't block the event loop either (the original code called it directly inside
`async def`s in three separate places).

### Embedding Model
- Model: all-MiniLM-L6-v2 (sentence-transformers), Dimension: 384
- Loaded via @lru_cache singleton in embeddings.py
- Downloaded from HuggingFace on first run; cached locally.
- Operations: encode(texts[]), encode_one(text), cosine_similarity(a, b), chunk_text(text, 300, 30)

### Concept Extraction (nlp/extraction.py)
- **Changed 2026-10-03: curriculum-style prompt (`EXTRACTION_PROMPT_VERSION =
  "v2-curriculum"`).** The old prompt asked for "the most important concepts" *in
  the supporting text*, so the graph mirrored whatever the sources happened to
  discuss. For "association football" (a real build) that was 5 arXiv abstracts:
  nodes like "Robotic Perception System", "Depth Estimation via CNN" and "Injury
  Measurement Tools", next to section headings ("Game Overview", "Terminology
  Origins") rather than things to learn. Its forced category list (Algorithms,
  Hardware, Research, Ethics…) pulled "Ethical Considerations" into a sports
  topic. The prompt now asks for the concepts *a beginner must learn* to
  understand the topic. They come in learning order and must be concrete (no
  meta headings, no niche papers or tools). Each one carries its direct
  `prerequisites` (labels from the same list). The categories are now domain-neutral:
  Foundation / Core Concept / Technique / Application / Context. The
  prerequisites become the graph's `prerequisite_of` edges (see Relation
  Classification), so one call yields both nodes and learning-path ordering.
  `max_tokens` went from 3072 to 4096 for the prerequisite lists.
  **Validated live 2026-10-03 on Groq (`openai/gpt-oss-20b`), one call per build:**
  - *Association football soccer:* 11 nodes and 10 prerequisite edges, all on-topic.
    The path was Basic Equipment → Pitch Layout → Players and Positions → Laws of
    the Game → Play Phases / Match Duration / Offside Rule → Passing, Defensive
    Tactics, Set Pieces → Shooting. The previous build of the same query had
    robotics, depth-estimation, concussion and ethics nodes.
  - *Photosynthesis:* 12 nodes and 12 edges: Light → Photopigments → Chlorophyll →
    Photosystems → Light-Dependent Reactions → Calvin Cycle → …, with advanced
    topics (photoinhibition, efficiency) last.
  - *Quantum computing:* 8 concepts extracted; the relevance filter dropped
    "Dataflow Graph Representation" (0.17, an arXiv tangent), leaving 7 nodes in
    one chain: Qubits → Superposition → Entanglement → Gates → Circuits →
    Measurement → Hybrid algorithms.

  All three builds came out fully connected, used no fallback, and took 3–19 s.
  Known rough edges: labels can still include a meta word ("Laws of the Game
  Overview"), and a broad topic can come back thin (7 nodes for quantum computing).
- `prior_knowledge` (if supplied) is folded into the prompt, biasing extraction
  toward what builds on it.
- Concept count: the prompt asks for *at most* `initial_graph_node_cap` concepts,
  fewer if the topic is narrow, and explicitly says not to pad. It used to ask for
  a hardcoded "6–10". The floor of 6 made narrow topics get padded with tangential
  concepts. The ceiling of 10 had drifted from the cap of 12, so the cap only
  fired when the LLM ignored the prompt. The upper bound is deliberately kept,
  not removed. Anything past the cap is discarded by `build_graph()` anyway. An
  unbounded list risks truncating the JSON within the `max_tokens=3072` budget,
  which drops the build to spaCy. The batched relation call's output grows with
  roughly n² pairs. And without a target, different providers in the fallback
  chain return very different counts for the same topic. Node expansion uses the
  same prompt and keeps only the first 6 new concepts that aren't duplicates
  (`tasks.py`), so for expansion the limit just means more spare candidates.
- Fallback: spaCy en_core_web_sm -- named entities + noun chunks (2-5 words), scored by frequency.
- Caching: Redis cache keyed by hash of "{EXTRACTION_PROMPT_VERSION}::{topic}::{max_concepts}::{sorted prior_knowledge}::{text[:500]}". 30-day TTL.
  `max_concepts` is in the key so that changing `initial_graph_node_cap` doesn't serve
  extractions cached under a different limit; the prompt version is in it so results
  cached under an older prompt can't mask a new one. **Bump `EXTRACTION_PROMPT_VERSION`
  whenever the prompt's wording or output shape changes.**
- LLM may wrap response in JSON fences despite instruction; handled via `llm.strip_json_fences()`.

### Multi-Key Providers and Ensemble Relation Classification (new)
- Each provider's `*_api_key` setting now accepts one key or several
  comma-separated keys. `llm.py::_acquire_key()` picks whichever key for that
  provider has capacity available right now (its own RPM/TPM bucket per key)
  rather than funneling every call through one shared bucket -- multiple keys
  for the same provider genuinely raise its effective throughput instead of
  being an idle spare. `complete_text_from()`/`complete_json_from()` call one
  named provider directly, no fallback, for callers that want independent
  answers from several specific providers at once.
- **Fixed**: among keys with capacity, selection used to always prefer index 0
  first (`for i, bucket in enumerate(buckets)`). Since each key's bucket
  refills continuously between requests, key 0 almost never ran dry from the
  client-side RPM/TPM check alone, so it soaked up nearly every call and hit
  the *provider account's* real quota (daily caps, etc. that the local bucket
  doesn't model) while keys 1-4 sat idle. `_acquire_key()` now tracks a
  per-key `_last_used` timestamp and, among keys with capacity, picks whichever
  was used longest ago (LRU) -- this is what actually makes 5 keys behave like
  5x throughput instead of "1 key until it breaks, then failover." Only
  `gemini` and `groq` are in the default `LLM_PROVIDER_CHAIN` currently
  (`backend/.env`) -- Cerebras needs a billed account and Mistral has no key
  registered; both remain valid provider names in `_OPENAI_COMPAT_PROVIDERS`
  and can be re-added once usable.
- `extraction.py::classify_relations_ensemble()` wraps the batched relation
  prompt: sends it concurrently to up to `relation_ensemble_size` (default 2)
  distinct configured providers and uses cross-provider agreement on a given
  edge as its confidence, rather than one model's self-reported (uncalibrated)
  number. Also more resilient than a single call -- one provider failing no
  longer means the whole step returns an edgeless graph, since any other
  provider that answered still contributes edges. Degrades automatically to a
  single `classify_relations_batched()` call when only one provider is
  configured or `relation_ensemble_size <= 1`, so it's the default call
  `graph_builder.py` makes unconditionally.
- **Removed 2026-10-03: orphan repair (`classify_orphan_edges()`).** It asked the
  LLM to connect every node left without edges, and the LLM obliged even for
  off-topic nodes. "Injury Measurement Tools related_to Game Overview" (0.75) in a
  football graph made a tangent look like it belonged. Nodes the classifier
  leaves unconnected are now treated as tangents and dropped by the connectivity
  filter (Graph Builder below). This also saves one LLM call per build.

### Relation Classification (nlp/extraction.py)
- **`relation_mode = "curriculum"` (default since 2026-10-03):** no relation call
  at all. `graph_builder.curriculum_edges()` turns each concept's `prerequisites`
  into `prerequisite_of` edges, at a fixed confidence `CURRICULUM_EDGE_CONFIDENCE =
  0.8`, since the prompt doesn't ask for a per-edge number. Labels match
  case/whitespace-insensitively and through dedup aliases. A whole graph build is
  now **one** LLM call (extraction), down from 2–4 (extraction + ensemble + orphan
  repair). The graph holds only prerequisite edges, which is the relation a
  learner acts on. If extraction yields no prerequisites (spaCy fallback, or an
  older-format result), it falls back to the batched classifier below.
- **`classify_relations_batched()` (`relation_mode = "batched"`, and the fallback
  above):**
  a single LLM call receives the entire numbered concept list and returns the
  complete typed edge list as `{source, target, relation, confidence}` with
  1-based indices. This is the fix for a genuinely unworkable design: the previous
  one-call-per-pair approach makes 132 sequential calls for a 12-node graph, which
  against a real free tier (e.g. Gemini's 10 RPM / 250 RPD) takes ~13 minutes and
  exhausts a daily quota in two graph builds.
- **`classify_relation()` (legacy, `relation_mode = "pairwise"`):** the original
  one-call-per-pair classifier, kept specifically so the ablation study (§19) can
  compare batched vs. pairwise quality and cost.
- Edges with confidence < `relation_confidence_threshold` (default 0.5) are discarded.
- **New: one edge per concept pair** (`graph_builder.one_edge_per_pair()`), the
  highest-confidence one, with `prerequisite_of` winning ties. The batched
  classifier routinely returned two contradictory edges for one pair (e.g. "Game
  Overview prerequisite_of Pitch" *and* "Pitch subtopic_of Game Overview"), which
  rendered as a tangle and meant nothing extra.
- Fallback on any failure: `{relation: "related_to", confidence: 0.3}` -- below the
  0.5 threshold, so it's correctly discarded rather than accepted (the previous
  revision's stated fallback confidence of 0.5, which passed the threshold and
  produced a fully-connected graph, was the actual code's real default when no
  client was configured -- since fixed, see §6).

### Graph Builder (nlp/graph_builder.py)
- Deduplication: Cosine similarity >= 0.92 between concept embeddings triggers
  merge. Now a standalone, unit-tested function (`deduplicate_concepts()`) rather
  than inline in `build_graph()`.
- **Fixed (dedup chaining):** each cluster's comparison vector is now a running
  centroid of every member merged into it so far, not the original anchor
  concept's embedding held fixed forever. Plain single-linkage-to-the-anchor is
  prone to chaining -- concept C can be a near-duplicate of concept B, but if B
  already merged into A, C is only ever compared against A's original vector and
  may fail to merge even though it's really a duplicate of B. The persisted node
  embedding is the final centroid, not the anchor's original vector.
- Node cap: `initial_graph_node_cap` is now actually applied to the deduplicated
  concept list (previously defined in config but never enforced).
- **Fixed (node cap was positional):** capping used to be `deduped[:cap]` --
  whichever concepts the LLM/spaCy happened to list first survived, with zero
  relevance signal. spaCy-fallback concepts are ranked by
  `_rank_by_textual_salience()` (how often the label or any merged alias appears in
  the source text) before capping. *Changed 2026-10-03:* LLM concepts keep their
  extraction order instead, because the curriculum prompt lists them
  most-foundational-first, so that order is now the signal. Salience over a
  research-heavy corpus would have favoured exactly the wrong concepts.
- **New 2026-10-03: off-topic filter** (`relevant_indices()`): concepts whose
  "label: description" embedding has cosine similarity below
  `concept_relevance_threshold` (0.20) to the topic query are dropped, never below
  `MIN_GRAPH_NODES` (5). spaCy concepts are compared by label only, since their
  templated description makes everything look relevant. **This is a deliberately
  weak safety net.** Calibrated on the stored graphs, on-topic "Pitch and Field
  Features" scored 0.34 while off-topic "Information Retrieval System" scored 0.37.
  The ranges overlap, so only clear outliers (≈0.08–0.16) are cut. Relevance is
  really fixed by the prompt, the sources and the connectivity filter.
- **New 2026-10-03: connectivity filter.** After relations are built, only the root
  node's connected component (undirected) is kept, provided it has at least
  `MIN_ROOT_COMPONENT` (3) nodes; otherwise everything is kept and a `DEGRADED`
  line is logged. Disconnected islands (the football build had a separate robotics
  cluster) are tangents a learner can't reach from the topic. Prerequisite chains
  are bridged through dropped concepts (`project_edges()`: A→B→C with B dropped
  still yields A→C).
- **Fixed (root node was arbitrary):** `graph.root_node_id` used to be
  `nodes[0].id` on the unstated assumption that the first extracted concept is
  the topic itself. It's now whichever persisted node's embedding is closest
  (cosine similarity) to the topic query's own embedding.
- **Fixed (source linking was winner-take-all):** `_embed_and_link_sources()`
  used to attach each source document to only its single best-matching node.
  `node_sources` is a many-to-many table, so a document relevant to several
  concepts now links to every node it's similar to (cosine sim > 0.3), not just
  the top one -- RAG summaries for the other relevant nodes were silently
  missing this source before.
- Importance scoring: `apply_degree_centrality()` -- (in_degree + out_degree) /
  (N - 1) normalized degree centrality. Now a standalone function reused by both
  the initial build and node expansion (previously only ran once, at initial
  build; expanded nodes kept the 1.0 default forever).
- Topological sort: Kahn's algorithm over prerequisite_of edges.
  **Fixed 2026-10-03 (path order was effectively random):** plain FIFO Kahn's
  constrained only the nodes on prerequisite edges and emitted the rest in DB
  order. The football graph had 3 prerequisite edges for 12 nodes and started its
  path with "Terminology Origins", with "Rules and Regulations" at step 11. Among
  the nodes whose prerequisites are satisfied, the next one is now picked by
  priority: `depth_level` (core before expansions), then undirected distance from
  `graph.root_node_id`, then importance (descending), then label/id for stability.
  The same key sorts graphs with no prerequisite edges at all. `GET
  /topics/{id}/graph` passes the root too, so already-built graphs get the new
  order without a rebuild. (Re-ordering the stored football graph this way put
  "Game Overview" first and the robotics cluster last.)
- **Fixed (unbounded expansion size):** `max_expansion_depth` only ever bounded
  recursion depth, not total node count -- repeated expansion clicks on
  different nodes could grow a single graph without limit. A new
  `max_graph_nodes` setting (default 60) is now checked in `tasks.py::expand_node`
  before fetching sources (so an already-full graph doesn't waste an API call),
  and the per-call new-node limit is clipped to the graph's remaining budget.

### RAG Summarizer (nlp/summarizer.py)
- Retrieves top-k source chunks by cosine distance using a parameterized pgvector
  query. **Fixed a genuine, previously-undetected bug**: the query used
  `:vec::vector` with no space before the cast, which SQLAlchemy's `text()`
  bind-parameter parser mis-tokenizes (reads the bind name as `ve`, not `vec`),

- Generates summary via the free-tier LLM chain with depth-specific word count
  targets, now via `await complete_text(...)` rather than a direct synchronous
  Anthropic call inside an `async def`.

### 12.9 Pipeline Observability (`app/logging_utils.py`) -- new

**Why:** the fallbacks above are silent by design, so a dead provider, a truncated
JSON answer, or a poisoned cache entry used to produce a healthy-looking `ready`
topic with nothing in the logs linking the symptom to its cause. Every step, LLM
attempt and degradation is now logged and correlated per run.

- **One setup for both processes.** `configure_logging()` is called by `main.py`
  (API) and, via the Celery `setup_logging` signal in `worker.py`, by the worker --
  connecting that signal stops Celery installing its own root-logger config, so the
  worker no longer ignores the app's format. Idempotent. Format:
  `time | LEVEL | run_id | logger | message`. `run_id` is `topic:<first 8 chars of
  topic id>` (or `expand:<node id>`, `trends:<topic id>`), injected on every record via a
  log-record factory + a `ContextVar`, so one build can be grepped out of interleaved
  worker output: `docker compose logs worker | grep topic:1a2b3c4d`.
- **`step(name)`** logs `STEP x START` / `DONE in Ns key=val` / `FAIL`. Used for
  `fetch_sources`, `extract_concepts`, `build_graph` (and the same two in expansion).
- **`degrade(stage, reason)`** logs `DEGRADED stage=... reason=...` at WARNING and
  records it on the run. Called for: spaCy fallback (with the *reason* the LLM path
  failed), a cache hit that serves a stale spaCy result, failed/partial relation
  classification, zero-edge graphs, summaries that fell back to raw passages, and a
  RAG index with no doc->node links.
- **`SUMMARY` line:** every run ends with exactly one -- status, total time, per-step
  timings, LLM calls ok/failed, which providers actually served them, and the list of
  degradations. WARNING level if anything degraded or failed, INFO otherwise. So
  `grep SUMMARY` + `grep DEGRADED` answers "did this topic get the real pipeline?".
- **LLM layer (`llm.py`):** `LLM OK` (provider, model, key `#i/n`, latency, prompt/out
  size, `finish_reason`, token usage when reported), `LLM FAIL` (HTTP status **and
  response-body excerpt**, so a retired model's `model_not_found` is visible, plus which
  provider it falls through to), tenacity retry lines, rate-limit waits,
  `LLM TRUNCATED` when `finish_reason == "length"` (the reasoning-token overrun from
  §12), and `LLM JSON PARSE FAIL` with the head and tail of the raw answer. API keys
  are never logged (only a key index).
- **Stale-cache visibility:** `_spacy_extract` tags each concept with
  `"_source": "spacy_fallback"`; that tag survives the Redis cache, so
  `extract_concepts` can flag a cache hit that is silently re-serving a degraded result
  (the 30-day-TTL hazard described in §12). The tag is ignored by graph building.
- **Other steps:** per-connector result count/size/latency and named connector failures
  (`aggregator.py`), dedup merges with cosine scores, cap drops, relations
  proposed/kept/below-threshold, orphan repair, edge-type counts, learning-path mode
  (topological vs importance fallback vs cycle), RAG chunk/link counts, summary
  retrieval similarity range.
- `httpx`/`httpcore` are set to WARNING (superseded by the `LLM OK` line). Tests:
  `tests/test_logging_utils.py`.
- **Not done:** the trace is logs-only. It is not persisted to the DB and not sent over
  the WebSocket, so the UI cannot yet show a "degraded" badge.

## 13. Asynchronous Processing (Celery)

### Configuration (worker.py)
- broker: redis://redis:6379/1, backend: redis://redis:6379/2
- include: ["app.tasks"], serialization: JSON only
- concurrency: 4, **prefork pool** (confirmed via `ForkPoolWorker-N` in live logs --
  the previous revision's "thread-based concurrency" claim was incorrect),
  prefetch_multiplier: 1

### Async-in-Sync Pattern (fixed)
All tasks use `asyncio.run(coro)` to create a new event loop per task call. The
SQLAlchemy async engine's connection pool is disposed *inside that same loop*,
immediately before it closes, via `tasks.py`'s `_run()` wrapper -- fixing a crash
that reproduced on the second task run in any given forked worker process
(including every retry), confirmed live in this project's own containers. See
§5.2 for the full story, including why the first fix attempted (disposing in a
second, separate `asyncio.run()` call afterward) didn't actually work.

### Task Retry Policy

| Task | max_retries | countdown |
|------|-------------|----------|
| build_topic_graph | 2 | 10s |
| expand_node | 2 | 10s |
| detect_trends | 1 | 30s |

On final retry failure: task enters FAILURE state in Celery backend. For build_topic_graph, topic.status = "failed" and error WebSocket event are sent.

## 15. Frontend Architecture

### Routing
No React Router. App.tsx renders LandingPage when topicId === null and
GraphWorkspace otherwise. **Fixed:** state (including topicId, graphData,
learningPath, pipelineStep, and progress) is now persisted to localStorage via
Zustand's `persist` middleware, so a page refresh no longer loses the current
graph. UI-only state (panel open/closed, selectedNodeId) is deliberately excluded
from persistence.

### State Management (Zustand, src/store/appStore.ts)
Single global store, now with selective localStorage persistence (see above).

| Field | Purpose |
|-------|--------|
| topicId | Current topic UUID; drives page routing |
| graphId | Current graph UUID; used for search |
| graphData | Full GraphData (nodes + edges + learning_path) |

| selectedNodeId | Currently selected node; drives drawer |
| progress | Record<nodeId, status> |
| learningPath | Ordered array of node IDs from server |

### Cytoscape Graph (GraphCanvas.tsx)
Key architectural decision: The Cytoscape instance is created ONCE on mount and
never destroyed/recreated. Graph data is synced incrementally:
1. On graphData change: compute diff, call cy.add() for only new elements.
2. Only run fcose layout on elements that changed, with randomize:false to preserve existing positions.
3. On selection/progress change: call `cy.style(...)` to re-style without a layout re-run.

**Fixed a real runtime bug:** this used to call `cy.setStyle(...)`, which does not
exist on Cytoscape's `Core` type -- the real method is `cy.style(...)`. This would
have thrown `TypeError: cy.setStyle is not a function` and aborted the whole effect
the first time a user clicked any node, silently breaking all
selection/progress-based re-styling. Caught by re-enabling `tsc --noEmit` (which
had never been run clean before -- see §18) rather than by reading the code.

Node event handlers use useAppStore.getState() to avoid stale closure issues.
Node sizing: Math.max(30, Math.min(60, 30 + importance_score * 10)) pixels. Range: 30-60px.

**Reading the graph as a route (2026-10-03).** A user looking at a built graph
couldn't tell where to start or what the edges meant. The canvas now:
- shows each node's learning-path step number in its label ("3. Offside Rule"),
  matching the "Start Here" panel. (`pathIndex` used to be set on nodes and never
  styled.)
- rings the **next step** (the first path node not marked learned) in amber;
- draws only `prerequisite_of` edges by default, plus whatever attaches an
  expanded (depth ≥ 1) node so it doesn't float. A legend checkbox "Show all
  relation types" reveals the rest. If a graph has no prerequisite edges,
  everything is shown.
- **Fixed: edge labels rendered permanently.** Cytoscape has no `:hover` selector
  state, so the old `edge:hover` style rule never acted as a hover rule, and every
  edge label was drawn all the time (the overlapping
  "subtopic_of/prerequisite_of/related" text in screenshots). Hover is now tracked
  with `mouseover`/`mouseout` toggling an `.hovered` class.
- has a small top-left legend: numbers = suggested order, amber ring = next step,
  A → B = learn A before B.

### Data Fetching (React Query v3)
- Summaries: cached 30 minutes, fetched only when summary tab is active.
- Sources: cached 10 minutes, fetched only when sources tab is active.
- Trends: cached 30 minutes, fetched only when TrendsPanel is open.

### WebSocket Client (hooks/useWebSocket.ts)
- One WebSocket per channelId. 25-second heartbeat ping.
- **Fixed:** now reconnects with exponential backoff (1s -> 15s cap) on an
  unexpected close -- previously there was no reconnection logic at all, so one
  dropped connection meant the user missed every subsequent pipeline/expansion
  event until a manual page reload.

## 17. Error Handling and Retries

### Backend API
- FastAPI raises HTTPException with appropriate status codes.
- The get_db() dependency handles session rollback on exception.

### Celery Task Error Handling
On failure: sets topic.status="failed", broadcasts error event, then calls
self.retry(). **Retries now actually work** (see §5.2/§13 -- previously the
second attempt at any task in a given worker process crashed with a database
connection error before its own logic ran, which itself then triggered another
retry, compounding). If max_retries exceeded, exception propagates and task state
= FAILURE. expand_node does NOT set any DB status on failure. detect_trends fails
silently after one retry.

### Cache Error Handling
All cache operations are wrapped in try/except; errors logged at WARNING level; operation silently degrades.

### Frontend Error Handling
- LandingPage.tsx: Catches axios errors on topic creation; shows static error message.
- GraphWorkspace.tsx: Catches polling errors silently (empty catch block).
- NodeDetailDrawer.tsx: React Query handles loading/error states; no explicit error UI on mutation failure.
- WebSocket: onerror logs to console; **now recovers via automatic reconnection**
  rather than staying dead until a manual reload (see §9, §15).

### Retry Behavior Summary

| Component | Retry mechanism | Behavior |
|-----------|----------------|----------|
| Celery tasks | self.retry(countdown=10) | Up to 2x retries; **now actually succeed on retry** |
| Source connectors | None | Exception caught at aggregator level |
| Redis cache | None | Silent fallback to uncached path |
| LLM provider chain | tenacity, 3 attempts per provider on 429/5xx | Falls through to the next configured provider, then spaCy/passage-concat |
| Frontend polling | setInterval continues | Silently catches errors |
| Frontend WebSocket | Exponential backoff, 1s-15s cap | **New** -- previously no reconnection at all |

## 19. Evaluation / Ablation Study (backend/eval/) -- new

Per the project's own implementation plan (`06_Implementation_Plan...md`, Phase 7),
this compares four ways of typing the edges between a fixed set of concepts:

| Variant | What it does | API calls per graph |
|---|---|---|
| `keyword` | co-occurrence in the same ~300-word chunk of source text | 0 |
| `embedding` | cosine similarity of local sentence embeddings | 0 |
| `llm_pairwise` | the legacy one-call-per-pair classifier | O(n^2 - n) |
| `llm_batched` | the current default: one call classifies the whole graph | 1 |

`keyword` and `embedding` can only ever say `related_to` or nothing; `report.py`
scores them on both the full 5-way relation label and a binary "any relation
detected" axis so they aren't penalized purely for a distinction they were never
designed to make.

**Pipeline:** `capture_fixtures.py` freezes a source corpus per topic (so later runs
are offline and don't burn quota re-fetching); `run_ablation.py` runs one or all
variants against `labels/{topic}.csv` (hand-labeled `concept_a,concept_b,gold_relation`
pairs); `report.py` aggregates every prediction file into `summary.csv`, a
confusion matrix per (topic, variant), and an `f1_comparison.png` bar chart.

**Verified end-to-end** with the bundled 14-pair starter set for "quantum
computing" (`labels/quantum_computing.csv`).

**Results, re-run 2026-10-02** (the previous `eval/out/` files dated 2026-09-12
were produced while every LLM provider was silently dead (see §0), so both LLM
variants had predicted `no_relation` for every pair and scored the same as an
empty baseline; those numbers are obsolete):

| Variant | Macro F1 (typed, 5-way + none) | Binary F1 (any relation) | API calls | Wall clock |
|---|---|---|---|---|
| `keyword` | 0.14 | 0.80 | 0 | 0.0 s |
| `embedding` | 0.16 | 0.91 | 0 | 2.7 s |
| `llm_pairwise` | 0.19 | 0.92 | 14 | 165.7 s |
| `llm_batched` | **0.39** | 0.80 | 1 | 5.5 s |

Gemini's free daily quota (20 requests/day for the configured model) ran out
during this session. These runs (and the ambiguity eval) very likely used it up
themselves; it was not checked beforehand. Both LLM variants ended up on **Groq**
via the fallback chain. Read these
numbers with the following caveats in mind:

- **n = 14 pairs, one topic, one run.** A single pair flips macro F1 by several
  points; there are no confidence intervals and no repeat runs to measure LLM
  nondeterminism. They show that the harness works. They are not yet a research
  finding.
- **Which provider answered isn't recorded.** `summary.csv` and the per-pair CSVs
  log neither provider nor model, so a run on Gemini and a run on Groq are
  indistinguishable after the fact. Record it before running the full study.
- **`subtopic_of` direction is defined inconsistently.** The LLM prompts define it as
  "the *first* concept is a sub-area of the *second*". The gold labels
  (`Quantum Algorithm,Shor's Algorithm,subtopic_of`) and `expand_node`'s
  parent→child edges both use the opposite (parent-first) reading. In this run
  the batched model happened to follow the label convention and the pairwise one
  answered `prerequisite_of`. Pick one convention and fix the prompt, the labels
  and `tasks.py::expand_node` together.
- **`llm_batched` scoring is direction-sensitive even for symmetric relations.** It
  looks up only `(a, b)`. A `related_to` emitted as `(b, a)` counts as `no_relation`.
- **Nothing scores the learning path**, which is the output the primary goal depends
  on. The PRD's metric is a human-rated learning-path accuracy ≥ 4.0/5.

**Ambiguity eval (`run_ambiguity_eval.py`, 20 labeled queries, re-run 2026-10-02):**
accuracy 0.90, precision 1.00, recall 0.80, F1 0.89. Both misses were false
negatives (`Rugby`, `Cricket` not flagged as ambiguous).

**This starter set is explicitly not the research-grade dataset the implementation
plan calls for** -- that's 150-300 hand-labeled pairs across 2-3 seed topics
(Quantum Computing, AGI, Blockchain are named), and the plan frames labeling as a
human task, not something to automate. `eval/README.md` documents how to extend
it. The plan's own contingency (§4) allows shrinking to two seed topics if labeling
runs long.

also comparing a percentage-scale constant against an unscaled ratio, so it was

### 4. GraphOut.learning_path Type Mismatch -- **FIXED**

`GraphOut.learning_path` is now typed `list[str]`, matching the string values the
code has always actually sent. (Pydantic's coercion meant this never caused a
visible bug, but the type annotation was wrong.)

### 5. Blocking I/O in Async YouTube Connector -- **FIXED**

`YouTubeConnector._get_transcript()` now runs via `loop.run_in_executor()` rather
than being called directly inside an `async def`.

### 6. Reddit Deprecated asyncio.get_event_loop() -- **FIXED**

Now uses `asyncio.get_running_loop()`.

### 7. Unused Import in expand_node -- **FIXED**

The dead `from app.nlp.graph_builder import build_graph` import in `tasks.py` is removed.

### 8. video_extractions Table Has No UI Path -- **FIXED**

`NodeDetailDrawer.tsx`'s Sources tab now has a "Generate notes & quiz" action per
YouTube source that calls this endpoint and renders the result, including a
click-to-reveal quiz.

### 9. (New) SourceDocument.metadata Reserved-Name Crash

Not in the previous revision at all: `metadata` collides with `Base.metadata`
(SQLAlchemy's declarative base reserves this name), so `import app.db.models`
raised `InvalidRequestError` before any application code ran. Fixed by renaming the
Python attribute to `doc_metadata` while keeping the same `"metadata"` column name.

### 10. (New) requirements.txt Had an Unconditional Dependency Conflict

`fastapi==0.111.0` unconditionally requires `fastapi-cli>=0.0.2`, which requires
`typer>=0.12.3`; `spacy==3.7.4` requires `typer<0.10.0`. No version of `typer`
satisfies both. Fixed by bumping spaCy to 3.7.5, which relaxed its pin to
`typer<1.0.0`.

### 11. (New) WebSocket Real-Time Was a Guaranteed No-Op, Not a Scaling Concern

See §9 in full. The previous revision filed this under "scalability" (§22); it was
actually a complete functional failure in every deployment this project has run.

### 12. (New) asyncio.run()-per-Celery-task Crashed on Retry

See §5.2/§13. Not gevent/eventlet-specific as previously speculated -- reproduced
live with Celery's actual default pool.

### 13. (New) Wikipedia API Changes Since This Code Was Written

Missing `User-Agent` (403) and the fully-decommissioned `mobile-sections` endpoint
(also 403, silently degrading content quality). See §11.

### 14. (New) arXiv XML Parsing's ElementTree Truthiness Bug

`entry.find(...) or {}` is falsy for any leaf element with text but no child
elements -- meaning `{}.text` raised on every entry. See §11.

### 15. (New) RawDocument Cache-Hit Type Bug

`published_at` came back as a raw string (not a `datetime`) on a cache hit, in
every connector. See §6, source_documents.

### 16. (New) GraphCanvas.tsx Called a Nonexistent Cytoscape Method

`cy.setStyle(...)` isn't a real method; the correct one is `cy.style(...)`. Found
via getting `tsc --noEmit` to run clean for the first time, not by reading the
code. See §15.

### 17. (New) Both Raw pgvector Queries Had a Silent SQL Bind-Parameter Bug

`search.py` and `summarizer.py` both build a raw SQL query containing
`:vec::vector` (a named bind parameter immediately followed by Postgres's `::`
cast operator, no space between them). SQLAlchemy's `text()` bind-parameter
parser mis-tokenizes this: `text("SELECT :vec::vector")._bindparams.keys()`
returns `['ve']`, not `['vec']` -- confirmed directly. Both endpoints therefore
sent malformed SQL to asyncpg on every single call and always raised
`PostgresSyntaxError: syntax error at or near ":"`, surfacing to the client as an
HTTP 500 (and, confusingly, as a CORS error in a browser's console, since
Starlette's raw error-response path for an unhandled exception doesn't carry the
CORS middleware's headers, which browsers then misreport as a CORS failure rather
than what actually happened). The previous revision's claim that these queries
were "fixed: parameterized, no SQL injection" was true about injection safety and
false about the query actually working -- neither endpoint had ever executed
successfully. Found only by clicking a node in a real running browser session and
reading the console, confirmed by inspecting SQLAlchemy's parsed bind names
directly, and fixed with a one-character change in both files (`:vec ::vector`,
a space before the cast). Verified live afterward: both the summary endpoint and
semantic search now return correct results.

## 22. Technical Debt and Risks

### Architectural Risks

**Issue: In-memory WebSocket registry, cross-process**
- Severity: was CRITICAL (a complete functional failure, not a scaling concern) -- **FIXED**, see §9.
- Location: backend/app/api/ws.py

**Issue: No schema migration system**
- Severity: MEDIUM -- unchanged, and a deliberate scope decision (see §10, §20)
- Location: backend/app/db/session.py: init_db()
- Evidence: Uses Base.metadata.create_all() instead of Alembic
- Consequence: Any column change requires recreating tables and losing all data.

### Security Risks

**Issue: No authentication on any endpoint**
- Severity: CRITICAL for any public deployment; out of scope for this project's
  actual use case (see §10)
- Location: All API routes in backend/app/api/v1/

**Issue: Default credentials in docker-compose**
- Severity: HIGH if deployed publicly; fine for local dev
- Location: docker-compose.yml
- Evidence: POSTGRES_PASSWORD: rabbit_secret hardcoded

**Issue: CORS restricted to localhost only**
- Severity: LOW for dev; blocker for staging/prod
- Location: backend/app/main.py
- Consequence: Any non-localhost deployment of the frontend will be blocked by CORS.

### Reliability Risks

**Issue: No WebSocket reconnection** -- **FIXED**, see §9/§15.

**Issue: O(n^2) LLM calls during graph build** -- **FIXED**, batched by default; see §12. The
legacy pairwise mode is retained only for the ablation study (§19).

**Issue: Celery task retries re-run full pipeline**
- Severity: MEDIUM -- unchanged. On failure midway, all source fetching and
  extraction are re-executed. Not idempotent. (Retries now at least *succeed*
  rather than crashing outright -- see §5.2 -- but they're still not incremental.)

**Issue: PostgreSQL may not be ready at backend startup** -- **FIXED**. Compose
healthchecks (`pg_isready`, `redis-cli ping`, an HTTP check) with
`depends_on: condition: service_healthy` now gate startup order.

**Issue: asyncio.run()-per-task engine/connection-pool crash** -- **FIXED**, new
finding not in the previous revision; see §5.2/§13/§21.13.

### Code Quality Risks

- `tasks.py: build_graph` dead import -- **FIXED** (removed).
- `cache.py: graph_layout_key()` dead code -- **FIXED** (removed).
- `python-jose`, `passlib[bcrypt]` unused dependencies -- **FIXED** (removed from requirements.txt).
- `prior_knowledge` field in TopicCreate -- **FIXED**, now actually threaded through (§6).
- Frontend never passed `tsc --noEmit` -- **FIXED** (§0, §18) -- six real errors, including the `cy.setStyle` bug above, sat undetected.

## 24. How to Run Locally

### Prerequisites
- Docker Desktop (Windows/Mac) or Docker + docker-compose (Linux)
- Internet access (for model downloads on first run, and for the source connectors/LLM calls)
- **At least one free-tier LLM API key is recommended** (Gemini, Groq, Cerebras, or
  Mistral -- see §12). Without any, the pipeline still runs end-to-end (verified),
  but falls back to spaCy for extraction and produces an edgeless graph.

### Setup

**1. Configure environment**
```bash
cp backend/.env.example backend/.env
# Edit backend/.env and fill in whichever free-tier keys you have:
# GEMINI_API_KEY=...
# GROQ_API_KEY=...
# CEREBRAS_API_KEY=...
# MISTRAL_API_KEY=...
# (YOUTUBE_API_KEY, REDDIT_CLIENT_ID/SECRET, SERPAPI_KEY are all optional too)
```

**2. Start all services**
```bash
docker-compose up --build
```
First run takes significant time (pulling images, installing Python packages --
now installing the CPU-only torch build, much smaller than before -- downloading
en_core_web_sm, and downloading all-MiniLM-L6-v2 on first task execution).
Healthchecks now gate startup order, so the backend won't try to connect before
Postgres is actually ready.

**3. Verify services**
- Backend: http://localhost:8000/health -> {"status": "ok"}
- Frontend: http://localhost:3000
- API docs: http://localhost:8000/docs

**4. Run the test suite (optional but recommended)**
```bash
docker compose exec backend pytest -v
```

**5. Run the ablation study (optional)**
```bash
docker compose exec backend python -m eval.capture_fixtures --topic "quantum computing" --slug quantum_computing
docker compose exec backend python -m eval.run_ablation --topic quantum_computing --variant all
docker compose exec backend python -m eval.report
```
See `backend/eval/README.md` for the full explanation, including what's a
demonstration starter dataset versus the research-grade corpus the implementation
plan calls for.

### Running Without Docker (Local Dev)

Not recommended on Windows: `torch==2.3.1` publishes no wheels for very recent
Python versions, and getting pgvector working natively on Windows is painful.
Docker sidesteps both. If you do run natively on Linux/Mac:

**Backend:**
```bash
cd backend
python -m venv rabbit_venv
source rabbit_venv/bin/activate
pip install torch==2.3.1 --index-url https://download.pytorch.org/whl/cpu  # CPU build, much smaller
pip install -r requirements.txt
python -m spacy download en_core_web_sm
# Ensure PostgreSQL (with pgvector) and Redis are running locally with credentials from .env
uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```

**Celery Worker (separate terminal):**
```bash
cd backend && <activate venv>
celery -A app.worker worker --loglevel=info --concurrency=4
```

**Frontend:**
```bash
cd frontend
npm install
npm run dev
```

### Important First-Run Notes
1. The all-MiniLM-L6-v2 model (~90MB) is downloaded from HuggingFace the first time a Celery task runs encode().
2. The PostgreSQL init.sql runs only once on first Docker volume creation.
3. The ANON_USER is seeded via init_db() every time the backend starts -- safe to restart repeatedly.
4. **Verified**: a full `docker compose down && docker compose build && docker compose up -d`
   cycle brings all five services up healthy from a clean image build -- this was
   actually exercised, not just described, as the final verification step of this
   revision.
